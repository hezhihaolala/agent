# 族谱关系推导与人物关系网设计

## 1. 背景与目标

当前产品可以保存人物、父母、配偶、兄弟姊妹和堂兄弟姊妹关系，但直接记录与可推导事实之间尚未形成统一规则，族谱页面也缺少人物关系网。

本次设计解决三个问题：

1. 根据已确认的亲属事实推导相关人物的父母、兄弟姊妹和配偶关系。
2. 区分数据库中的直接事实与系统推导结果，避免重复存储和静默覆盖。
3. 提供以人物为中心的交互式关系网，同时展示人物属性、关系和档案依据。

第一版继续使用 PostgreSQL，不引入 Neo4j、推导缓存表或双数据库同步。

## 2. 核心原则

- PostgreSQL 只保存管理员录入或确认的直接事实。
- 系统推导结果由确定性规则实时计算，不作为新的正式关系写回数据库。
- 直接事实与推导结果在 API 和界面中必须明确区分。
- 资料不完整时只说明已知部分，不推测未知父系或母系。
- 推导结果与直接事实冲突时保留原始数据，提示管理员核实，不自动覆盖。
- 智能体问答和关系网共用同一个关系引擎，避免两套规则产生不同答案。

## 3. 数据库方案

### 3.1 方案选择

采用“PostgreSQL 保存直接事实，规则引擎实时推导”。人物表相当于图中的节点，关系表相当于边，档案关联提供证据和核实状态。

暂不采用以下方案：

- 推导结果缓存表：需要处理复杂的缓存失效，当前数据规模没有必要。
- PostgreSQL 与 Neo4j 双写：增加部署、同步、监控和备份成本，当前路径查询复杂度不足以抵消这些成本。

如果未来人物达到数万且关系路径查询成为性能瓶颈，再根据真实指标评估递归 CTE、缓存表或图数据库。

### 3.2 人物属性

保留固定字段并增加少量预设扩展字段，不开放任意键值属性。

基础属性：

- 姓名、性别。
- 出生日期、去世日期。
- 籍贯、出生地。
- 生平简介。

预设扩展属性：

- 字、号。
- 曾用名或乳名。
- 字辈。
- 家庭排行。
- 职业。

人物继续保留核实状态，并可通过现有来源关联机制连接档案。配偶、父母等亲属信息属于关系，不放入人物属性。

### 3.3 直接关系

关系主体继续使用稳定人物 ID，不用姓名作为连接键。

- `parent`：有方向，`person_id` 指向子女，`relative_id` 指向父母。
- `spouse`：无方向。
- `sibling`：无方向，增加兄弟姊妹子类型。
- `paternal_cousin`：无方向；父系资料不足时允许直接记录，有完整父系路径时也可由规则推导。

兄弟姊妹子类型：

- `full`：同父同母。
- `paternal_half`：同父异母。
- `maternal_half`：同母异父。
- `unknown`：关系不详。

现有 `sibling` 数据迁移后子类型统一为 `unknown`，不得擅自认定为同父同母。

## 4. 关系推导规则

### 4.1 配偶

配偶关系保存一次，查询始终双向成立。智能体将“对象、爱人、配偶、丈夫、妻子”映射为同一类关系。

### 4.2 从父母事实推导兄弟姊妹

- 两人的父亲和母亲均已知且分别相同：同父同母。
- 父亲相同，双方母亲均已知且不同：同父异母。
- 母亲相同，双方父亲均已知且不同：同母异父。
- 只确认父亲相同但母系资料不全：显示“同父，母系不详”，不认定同父异母。
- 只确认母亲相同但父系资料不全：显示“同母，父系不详”，不认定同母异父。
- 没有共同的已知父母：不从父母事实推导兄弟姊妹。

### 4.3 从直接兄弟姊妹事实推导父母

- `full`：一方已知的父亲和母亲可作为另一方的推导父母。
- `paternal_half`：只推导共同父亲。
- `maternal_half`：只推导共同母亲。
- `unknown`：不推导任何父母。

推导只填补查询结果中的未知部分。如果另一方已有不一致的直接父母记录，则返回冲突状态和两组依据，不选择其中一组覆盖。

### 4.4 堂兄弟姊妹

存在“本人 → 父亲 → 父系祖父母 → 伯叔 → 子女”的可靠路径时，可推导堂兄弟姊妹。父系路径不完整时不猜测；管理员仍可直接记录并关联档案。

### 4.5 推导依据

每条推导结果包含：

- 推导称谓和目标人物。
- 完整人物路径与实际经过的关系 ID。
- `origin = inferred` 标记。
- 路径相关来源。
- 综合核实状态。

综合状态遵循“存在冲突优先，其次资料不足，全部依据已核实才是已核实”。

## 5. 关系网 API

新增以人物为中心的只读关系网接口。输入中心人物 ID、代数范围、关系类型和核实状态筛选；默认加载上下两代，避免一次返回整张族谱。

响应由两部分组成：

- `nodes`：人物 ID、展示名称、基础属性摘要和核实状态。
- `edges`：起止人物、关系类型、兄弟姊妹子类型、`direct/inferred` 来源、推导路径、核实状态和来源摘要。

点击人物时，前端使用其 ID 重新请求中心关系网。人物详情与来源可以按现有资源接口继续加载，关系网响应不携带完整生平或档案正文。

## 6. 前端关系网

使用 React Flow 构建只读交互式关系网，不要求底层使用图数据库。

### 6.1 默认布局

- 当前人物位于中心。
- 父母位于上方，配偶位于侧方，兄弟姊妹位于同层，子女位于下方。
- 默认显示上下两代。
- 点击其他人物后，该人物成为新的中心。
- 支持缩放、拖动画布、搜索人物及按关系和核实状态筛选。

### 6.2 直接与推导关系

- 直接事实使用实线。
- 系统推导使用虚线，并显示“系统推导”。
- 冲突关系使用明确警告状态，不能仅依靠颜色表达。
- 推导关系只读，不能直接编辑或删除。

### 6.3 人物详情

桌面端在关系网右侧固定显示人物详情，手机端使用底部抽屉。详情包含人物属性、直接关系、推导关系、核实状态和档案依据。

第一版不支持在画布上拖线创建关系。新增、编辑和删除仍从右侧详情进入现有表单，删除直接关系需要确认。

## 7. 智能体问答

常见关系问法继续优先由后端确定性解析。新增配偶同义词，并让以下查询共用关系引擎：

- “贺志豪的父母是谁”。
- “贺志豪的兄弟姊妹是谁”。
- “管应拉的对象是谁”。

回答必须说明结果是直接记录还是系统推导。推导资料不完整或存在冲突时，回答中明确提示，不把不确定结果写成确定事实。

## 8. 兼容与错误处理

- 保持已有人物、父母、配偶、堂兄弟姊妹、档案和审计数据不变。
- 为兄弟姊妹关系增加可空子类型，并通过数据库迁移将旧数据设为 `unknown`。
- 继续阻止自关联、重复关系和祖先循环。
- 同一人物出现矛盾父母或兄弟姊妹类型时返回冲突，不静默覆盖。
- 重名人物始终使用 ID 区分；需要人工选择时不自动猜测。
- 代数范围设置上限，防止单次关系网请求无边界扩张。

## 9. 测试与验收

### 9.1 后端

- 关系引擎覆盖同父同母、同父异母、同母异父、父系或母系不详和关系不详。
- 验证直接兄弟姊妹关系对父母的正确推导范围。
- 验证配偶双向查询和“对象”等同义词。
- 验证直接事实与推导结果冲突时不覆盖数据。
- 验证关系网代数边界、节点去重、直接边、推导边、路径和来源。
- 验证旧 `sibling` 数据迁移后完整保留且子类型为 `unknown`。

### 9.2 前端

- 验证人物切换中心、代数与关系筛选。
- 验证实线、虚线及文字标记。
- 验证右侧人物详情与移动端底部抽屉。
- 验证推导关系不可编辑，直接关系可进入维护流程。

### 9.3 端到端

1. 录入父母和兄弟姊妹类型，验证另一人的父母查询返回正确推导结果。
2. 建立配偶关系，验证两个方向及“对象”问法都能回答。
3. 打开关系网，验证直接边、推导边、人物切换和档案依据。

## 10. 第一版范围外

- Neo4j 或其他图数据库。
- 推导结果持久化缓存。
- 全族谱默认展开。
- 画布拖线创建或删除关系。
- 任意自定义人物属性。
- 根据年龄自动区分哥哥、弟弟、姐姐和妹妹。
